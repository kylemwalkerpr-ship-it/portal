## Implemented behavior

`lib/yqaaPrivacy.ts` and the existing `lib/messengerAi.ts` own the DM consent envelope. Scope is the existing conversation ID plus canonical client/student and attorney/consultant IDs; no separate tenant architecture or anonymous identity is invented. Missing consent, unavailable storage, wrong subject/provider/scope, and malformed epochs fail closed before message body retrieval, attachment reads, pricing preparation or model work. `force` cannot bypass consent. Already durable replies retain the existing replay behavior; replay does not create another effect or erase the original reply.

`GET /api/messages/conversations/[id]/privacy` returns only the authenticated customer participant's consent, or version 0 / granted false. `POST` accepts `{action, expectedVersion, requestId, explicitOptIn?}`; requestId is a UUID. Only grant with explicitOptIn true can activate consent. The subject always comes from existing verified portal auth, never the request body. The service-role RPC rechecks customer role, canonical participants, provider scope and CAS under the conversation row lock. Admin/provider participation alone does not authorize customer consent mutation. Cross-origin browser mutations deny. Responses use no-store for successful state reads.

Actions are `grant`, `forget`, `withdraw`. All advance the privacy epoch and remove `metadata.ai_memory`. Forget preserves the current granted status; withdrawal denies future DM preparation. Grant never imports pre-consent history. Each action advances `memory_after`; only messages strictly newer than this boundary are available to subsequent DM preparation. Derived snapshots carry consent_version, and snapshots from older versions are ignored. A conversation metadata trigger rejects stale memory resurrection by pending diagnostics. This deliberately forgets the whole snapshot; it is not a fact-level correction API.

The migration keeps the original Q01 atomic reply body with one gate after durable replay lookup and before effect insertion. It checks the consent version supplied in the reply envelope against the locked conversation's scoped consent. Mutation and commit use the same conversation row lock. Withdrawal/forget that wins the lock invalidates an old generation even after regrant; a reply already committed before withdrawal remains a retained message. An in-flight provider request may finish, but its stale reply/offer transaction is rejected. This does not claim cancellation of provider-side processing already begun.

The new tables have RLS enabled with explicit browser-deny policies and revoked browser privileges. Clerk portal authentication remains authoritative; the service role is trusted server infrastructure. Neither mutation receipts nor consent records store raw narrative. Receipts contain scope/subject IDs, UUID replay key, action, expected/result version and timestamps. Exact replay returns its original receipt without restoring old consent; request key reuse with changed arguments rejects. Current consent is read separately.

## Retention, invalidation and limits

Forgetting removes the derived `ai_memory` JSON snapshot and makes historical source messages unavailable to subsequent DM context preparation. There is no separate derived-memory cache/index in the inspected memory module. Pending closures are invalidated at durable commit rather than individually located or deleted.

Underlying conversation messages, offers, inquiries, transactions, existing pricing approvals, decision records and audit records are retained. This patch does not establish their legal retention periods or erase them, and makes no claim of legal erasure. Public knowledge/search indexes and anonymous analytics identities are separate existing systems; this patch neither links them to DM subjects nor implements their erasure. Cross-site linking remains unavailable and denies even when requested; supporting a separately consented linking flow is outstanding.
